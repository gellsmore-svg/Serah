## How to use this list

- Work in the order under [Fix order](#fix-order).
- Each H item has an **Acceptance** line. Turn it into a regression test in `tests/` before or alongside the fix. The repro script shows the shape of the test but is not a test suite.
- The mock engines read `user_evidence` only, and the mock curator ignores the taxonomy it is given. Tests for H1, H2 and H7 therefore need a recording engine, or a curator that inspects its inputs; asserting on mock scores will not catch these defects.
- If a fix changes documented behaviour, update the doc it contradicts in the same change. `TEMPORAL_MODEL.md`, `TAXONOMY.md` and `ARCHITECTURE.md` are the likely ones.
- Tick the box once the fix and its test are merged.
- Each H item is tracked as a GitHub issue with the same number: H1 is #1, through H8 as #8. Close each one from the fixing commit or PR with `Fixes #n`.

## High

### [ ] H1. A later import leaks future taxonomy into earlier days and never reviews new episodes on days already reviewed [repro r1] ([#1](https://github.com/gellsmore-svg/Serah/issues/1))

- **Where:**
  - `pipeline.py:73-76`: taxonomy stage marks are keyed on the day alone.
  - `taxonomy.py:154` (`_llm_review` catalogue) and `taxonomy.py:213-215` (the relevance filter) read the *live* `TaxonomyConcept.status`.
- **Problem:** Causal replay (§14) holds only when every day arrives before any later day is reviewed. A second import breaks it in two ways:
  1. **Leak.** An episode on a day that was never reviewed, earlier than days already reviewed, is checked against today's taxonomy. It can become relevant to a concept that was not active on its date.
  2. **Loss.** A new episode on a day that was already reviewed is skipped, because the day is stage-marked. In `relevant` mode it gets no relevance row, so it is never scored.
- **Repro:** After the demo, a new 7 March episode is marked relevant to `compression.obligation_pressure`, while `reconstruct('2024-03-07')` reports that concept as `proposed`. A new 3 March anger episode gets no relevance row.
- **Fix:**
  - Evaluate status and build the curator catalogue from `reconstruct(session, day)`, not the live table.
  - Key the taxonomy stage mark on `(day, hash of the day's sorted episode ids)`, so that a changed episode set re-reviews the day.
  - If a day earlier than the latest reviewed day gains episodes, the causally correct result means reviewing that day and every later day again. Either do that as an explicit "rebuild from D" step, or refuse and tell the operator. Do not silently review out of order.
- **Acceptance:** In the r1 scenario the 7 March episode is *not* relevant to `obligation_pressure`, and the new 3 March anger episode is reviewed and then scored in `relevant` mode.

### [ ] H2. Real System-1 engines are given the assistant's words and an English instruction as evidence ([#2](https://github.com/gellsmore-svg/Serah/issues/2))

- **Where:** `scoring.py:148-155` builds `state = {"user_evidence", "context", "evidence_rule"}`. The HTTP, Laya and Decider adapters pass that `state` through unchanged.
- **Problem:** A System-1 classifier scores the whole state as text; it cannot follow an instruction. Laya 0.3.20 serialises a dict state with `json.dumps` (`laya/common.py:17`) and tokenises all of it. For a user who wrote "Oui.", the model input includes the assistant's "You sound absolutely furious about this." and the sentence "Judge only user_evidence…". Assistant interpretation therefore reaches the scorer as evidence, which §17 forbids. The mock engine reads `user_evidence` only, so the existing test cannot see this.
- **Evidence:** The model input was confirmed with Laya's own `serialize_state`. The effect on scores was not measured, because Laya's weights are not downloaded on this machine.
- **Fix:** Give System-1 engines the user evidence only, for example `state = episode.user_text` as a string. Keep `context` for the LLM extractor, the curator and the LLM baseline, whose prompts already explain it. Drop `evidence_rule` from `state`, since the measurement question's instructions already carry that rule. If context is ever needed for a System-1 engine, add it as a separate, explicitly marked experiment setting.
- **Acceptance:** A recording engine test shows that System-1 requests contain no assistant text and no instruction text. Serah's docs describe what each engine is sent.

### [ ] H3. Scoring is not resumable, and one failure discards every result already paid for [repro r3] ([#3](https://github.com/gellsmore-svg/Serah/issues/3))

- **Where:**
  - `scoring.py:175-195`: every pending request goes to a single `engine.evaluate_batch`, and nothing is added to the session until it returns.
  - `engines/systemone.py:60-61` and `engines/decider_local.py:395-400` loop inside that single call.
  - `engines/laya.py:182` sends the whole history to one `predict_batch` with no batch size.
- **Problem:** A 5xx, timeout or rate limit on the last request discards every earlier observation and cache row. The next run pays for all of them again. That breaks §66 and makes the §64 cache useless in exactly the case it exists for. For a long history, a single Laya `predict_batch` also risks running out of memory.
- **Repro:** 127 engine calls and a failure on the last one: 0 observations and 0 cache rows kept.
- **Fix:** Score in chunks, one episode or N requests at a time. After each chunk, write the cache rows, observations and stage marks, then commit. On `EngineError`, stop but keep the completed chunks, and record the failure on the run. Pass a bounded batch size to Laya.
- **Acceptance:** In the r3 scenario 126 observations and 126 cache rows survive, and a rerun makes exactly 1 engine call.

### [ ] H4. Taxonomy reconstruction is non-deterministic, and reactivation is lost [repro r4, r5] ([#4](https://github.com/gellsmore-svg/Serah/issues/4))

- **Where:**
  - `manual.py:246` writes every human event with `sequence=0`, and so does `taxonomy.py:482` (`revise_definition`).
  - `taxonomy.py:48` orders by `(effective_on, sequence, id)`, where `id` is a random `uuid4`.
  - `taxonomy.py:56-101` has no branch for `CONCEPT_REACTIVATED`.
- **Problem:**
  - `add_concept(status="active")` writes `CONCEPT_PROPOSED` and `CONCEPT_ACTIVATED` on the same day with the same sequence. Their order during reconstruction is random, and when `PROPOSED` is applied second it overwrites the status.
  - A definition revision on the day a concept is proposed can be applied before the concept exists, and is then dropped.
  - A reactivated concept reconstructs as `deprecated`.

  §13 requires the taxonomy at any date T to be reconstructible, and §39 requires replay to be deterministic.
- **Repro:** 40 concepts added as active reconstruct with a different mix of `active` and `proposed` on each run (13/27 and 22/18 in two runs). A reactivated concept reconstructs as `deprecated` while its live status is `active`.
- **Fix:**
  - Give every writer a global, monotonic event sequence: an autoincrement column, or `max(sequence)+1` taken inside the transaction.
  - Order reconstruction by `(effective_on, sequence)` only.
  - Handle `CONCEPT_REACTIVATED`. Treat `CONCEPT_SPLIT` explicitly, even if it is a no-op.
  - Give `CONCEPT_PROPOSED` from `add_concept` the same full payload the curator writes: family, definition, guidance and version.
- **Acceptance:** r4 reconstructs all 40 as `active` on every run. r5 reconstructs `active`. A test also checks that reconstructing any date agrees with the live table after a full demo plus manual edits.

### [ ] H5. Re-importing a newer export drops new messages in conversations it has already seen [repro r2] ([#5](https://github.com/gellsmore-svg/Serah/issues/5))

- **Where:** `ingest.py:161-163` returns as soon as it finds a known conversation, so the per-message dedup at `:231-239` never runs.
- **Problem:** ChatGPT exports are cumulative, and continued conversations grow. Every message added after the first import is silently dropped: it produces no warning and is not counted as skipped. That breaks §16 ("avoid duplicate import" means don't store a message twice, not don't read a conversation twice) and criterion 6.
- **Repro:** The export holds 3 messages. After the second import, 2 are stored, with `messages: 0` and `warnings: 0`.
- **Fix:** For a known conversation, walk its messages anyway and insert only unseen external ids. Recompute `on_current_branch` from the new `current_node`. Update the conversation metadata. Report `new_messages` and `updated_conversations`, and warn when a previously stored message is missing from the new export. Downstream, the extraction stage marks already make new messages extractable. H1 covers the taxonomy side.
- **Acceptance:** r2 stores 3 messages and reports 1 new message.

### [ ] H6. "Linear" decay is really step-wise exponential [repro r6] ([#6](https://github.com/gellsmore-svg/Serah/issues/6))

- **Where:** `temporal.py:205` applies `level × (1 − 0.5·Δt/H)` to the current level at every activation and every UTC midnight (`:298`, `:317`).
- **Problem:** Linear decay does not compose: two steps of 24 h are not one step of 48 h. `TEMPORAL_MODEL.md` says linear is "halved at one half-life and zero at two", but with daily snapshots the level is 25 after two half-lives, not 0, and it never reaches zero. The result also depends on how many midnights fall between events, so a "linear vs exponential" comparison compares two nearly identical curves.
- **Repro:** An observation of 100 at 00:00 with a 24 h half-life gives 50 after 24 h, 25 after 48 h, and 6.25 after 96 h.
- **Fix:** Carry an anchor through `replay_concept`: the level just after the last activation, and its time. Compute linear decay from that anchor as `anchor × max(0, 1 − 0.5·(t − t_anchor)/H)`, whatever midnights fall in between. Exponential already composes, so it can use either form.
- **Acceptance:** r6 gives 50 at 24 h and 0 at 48 h. A test shows that linear snapshots do not change when extra midnights are inserted into the same interval.

### [ ] H7. Engines scored at different times get different target sets [repro r7] ([#7](https://github.com/gellsmore-svg/Serah/issues/7))

- **Where:** `scoring.py:199-213` (`_targets`) keeps only concepts that are active in the *live* table, and in `all-core` mode it uses the live locked set.
- **Problem:** Once a concept is merged or deprecated, any engine scored afterwards loses all of that concept's historical targets, even where the concept was active at the time of the evidence. Two engines in one experiment then no longer see "the same evidence and the same taxonomy" (§4, §6), and the chart shows a difference in coverage as if it were a difference in scoring.
- **Repro:** After the demo and a merge dated 2026, `obligation_pressure` has 1 observation for `mock` and 0 for an engine scored after the merge, on the same 2024 evidence.
- **Fix:** Derive each episode's targets from `reconstruct(session, episode_day)`: concepts active on that day, intersected with the relevance rows in `relevant` mode, or the locked core as of that day in `all-core` mode. This pairs with H1.
- **Acceptance:** In r7 the late engine has the same `obligation_pressure` observation count as `mock`.

### [ ] H8. There is no UI or CLI path to put a newly scored engine into an experiment ([#8](https://github.com/gellsmore-svg/Serah/issues/8))

- **Where:**
  - `cli.py:147`, `:156`: `serah replay --half-life-hours` clones the latest experiment's engine list. It only falls back to "engines with observations" when no experiment exists.
  - `frontend/src/App.tsx:570`: Replay settings offers only the current experiment's engines.
- **Problem:** After `serah demo`, running `serah score --engine laya` (or `jev`) stores observations that can only be charted through a raw `POST /api/experiments`. That fails criterion 28 (several System-1 model lines for anger), which is the project's central comparison.
- **Fix:** The Replay settings screen should list every engine that has stored observations, plus its availability from `/api/models`. The CLI should accept `--engines a,b,c` on `serah replay` (or gain a `serah experiment create` command).
- **Acceptance:** After scoring a new engine, it can be added to an experiment from both the CLI and the UI, and it appears in `/api/series`.

## Medium

### [ ] M1. Every API request re-initialises the database [repro r8]
`api.py:54-59` → `pipeline.open_session` → `db.session_scope` → `init_database`. Each request builds a new SQLAlchemy engine, runs `create_all`, seeds the core taxonomy and ensures 14 questions (repro: 51 inits for 50 requests, about 21 ms each). `day_view` (`queries.py:175-192`) and `_raw_points` (`queries.py:374-386`) also issue one query per observation. **Fix:** create one engine and sessionmaker per process at startup, keep `init_database` for startup only, and replace the per-row `session.get` calls with joins.

### [ ] M2. The local server serves personal text with no Host check [repro r8]
Any `Host` header is accepted (repro: `Host: attacker.example` → 200), which leaves DNS rebinding open against a server holding a real history. There is no auth, and `serah serve --host 0.0.0.0` prints no warning, although `PRIVACY.md` says not to do that. **Fix:** add `TrustedHostMiddleware` allowing `127.0.0.1`, `localhost` and the configured host. Warn, or require an opt-in flag, for non-loopback binds. Consider a per-launch token for POST routes.

### [ ] M3. Distributions with bins outside the scale are accepted [repro r9]
`distributions.validate_distribution` never checks bin values, so an LLM-baseline reply with bins 150/250 gives `expected_intensity` 200. `metrics()` computes concentration over however many keys the provider listed, so it is not comparable across engines. **Fix:** require bins in [0, 100]; for instrument answers, require exactly `INSTRUMENT_BINS`, and fill missing bins with 0 before computing concentration.

### [ ] M4. Alembic migrations are nominal
`alembic/versions/001_initial.py` runs `Base.metadata.create_all` against whatever the models are at run time. Startup also calls `create_all` and never stamps or upgrades. The first schema change will therefore drift silently on existing databases, and a `002` migration will conflict on fresh ones. **Fix:** freeze `001` as explicit DDL, run `alembic upgrade head` (or check the stamp) at startup, and stop calling `create_all` outside tests.

### [ ] M5. Extraction commits once, at the end
`pipeline.run_extract` commits after the whole `extract_pending` loop. A killed process loses every episode and stage mark from the run, which is costly with `SERAH_EXTRACTOR=llm` (§66). **Fix:** commit every N messages.

### [ ] M6. Manual taxonomy actions are dated with today's calendar date, not evidence time
`App.tsx:355` sends `new Date()` as `day`. Activating a candidate therefore writes `effective_on=2026-…` against 2024 evidence. That adds no relevance rows, so it has no scoring effect in `relevant` mode, and no historical reconstruction ever shows it. **Fix:** decide what a manual action means on the evidence timeline, for example "effective from the concept's first observed day" or a date the user picks. Apply it consistently, create relevance rows for supporting episodes when a concept is activated, and document the rule.

### [ ] M7. Telemetry and provenance gaps
Adapters capture `usage` in `DecisionResult`, but it is stored nowhere: `_cache_payload` and `ModelObservation` both drop it. Nothing records cost, cache hit rate or batch statistics at run level (§65). Observations do not carry the application version (§55). **Fix:** store `usage` on observations, and write request, cache and token totals into `ProcessingRun.stats`.

### [ ] M8. The trajectory UI is missing controls and detail from §42–§47
- There are no date-range, zoom or reset controls, and no x-axis date labels (`Chart.tsx`).
- In reservoir mode, hover does not show the raw observation, the concept version or the evidence count.
- The evidence drill-down never shows the reservoir event sequence, although `/api/observations/{id}` returns it.
- Annotations and self-ratings are never displayed.
- There is no compression view or timeline (§46).
- Engine colours are assigned after toggling, so they change when lines are toggled.
- The day view defaults to the demo date `2024-03-03`.

### [ ] M9. Human overrides are incomplete (§51)
There is no way to correct an extraction, and no graph-point annotation (annotations are per day). Split exists only in Python, not in the API or UI, and always forces family `emotion` (`manual.py:138`). Relationships cannot be removed.

### [ ] M10. Gaps in the candidate lifecycle
- Nothing moves weak candidates to `dormant` automatically (§12).
- `review.proposals[: max_proposals_per_day]` truncates the list before invalid proposals are filtered out, so invalid ones use up the cap (`taxonomy.py:218`).
- A proposal naming a locked concept changes that concept's `confidence` without writing an event (`taxonomy.py:332`).
- Excluded episodes still count toward support days.

### [ ] M11. The LLM curator and extractor receive incomplete context
The curator's catalogue includes status and support count but not candidate history or previous taxonomy events (§11). The extractor is given a discovered concept's `rationale` in place of its definition (`extract.py:143`). The `compression_discovery` and `taxonomy_candidate_review` prompts are never loaded.

### [ ] M12. One malformed file aborts an import
`ingest._load_documents` calls `json.loads` without handling errors, so one bad file in a directory or zip stops the whole import instead of recording a warning (§16).

### [ ] M13. The model version is not part of observation identity
`uq_observation_instrument` and the existence checks in `scoring.py` ignore `model_id`. Re-scoring the same engine with a new checkpoint or model is skipped, so model versions cannot be compared.

### [ ] M14. Type errors, and no backend type check in CI
Pyright reports 18 errors, among them real `None` handling in `ingest.py:195-207` and an optional operand in `api.py:318`. CI runs only ruff and pytest for the backend (§84). **Fix:** add pyright to the dev extras and to CI, and fix the errors.

## Low

- [ ] **L1.** `extract.py:46-58`: `previous_assistant` is never reset, so the second of two consecutive user messages gets a stale assistant message as context.
- [ ] **L2.** `api.py:62-66` maps every `SerahError`, including unknown ids, to 400. Use 404 for not found.
- [ ] **L3.** `scoring.py:108` falls back to the latest question when no question matches the concept version, so an observation's `question_version` can disagree with its `concept_version`.
- [ ] **L4.** `merge_concepts` accepts a merge of a concept into itself, and does not check that the target is active.
- [ ] **L5.** `create_experiment` does not validate `activation_gain` against [0, 1] (the value is silently clamped later), nor engine ids against the registry.
- [ ] **L6.** `llm_client.complete_model` does not retry transient HTTP errors, and neither does the System One adapter. `CuratorError` is also raised for extractor and baseline failures.
- [ ] **L7.** The default URL in `alembic.ini` (`./.serah/serah.sqlite`) differs from the application default (`~/.local/share/serah/serah.sqlite`). `env.py` overrides it, but the file misleads.
- [ ] **L8.** Raw mode draws a polyline between separate observations, which suggests continuity the data does not have.

## Test gaps

Add tests for:

- incremental import: a grown conversation, a new earlier day and a new episode on a reviewed day (H1, H5)
- what System-1 engines are sent, checked with a recording engine (H2)
- scoring resuming after a mid-run failure (H3)
- reconstruction agreeing with the live table after manual edits, including reactivation (H4)
- linear decay being independent of midnights (H6)
- engines scored at different times getting equal target sets (H7)
- API Host validation (M2)
- out-of-range distributions (M3)
- `alembic upgrade` from a stamped older revision (M4)
- adapter translation fixtures for real Laya and System One payloads

## Fix order

1. **H1, H7:** causal status everywhere. One change, `reconstruct(day)`, drives the curator, relevance and scoring targets.
2. **H2:** evidence-only state for System-1 engines.
3. **H3, M5:** chunked, committed scoring and extraction.
4. **H4:** global event sequence, and handling `CONCEPT_REACTIVATED`.
5. **H5, H6, H8.**
6. **M1, M2:** one engine per process, and Host validation.
7. **M4** before any schema change; **M3, M6–M14** after it; then the L items.
